# Architecture

**Проект:** Persephone Music
**Статус документа:** актуально для Stage 0
**Связанные документы:** [PROJECT_SPEC.md](PROJECT_SPEC.md), [docs/DATA_MODEL.md](docs/DATA_MODEL.md), [docs/adr/](docs/adr/)

## 1. Общая форма

Persephone Music — **модульный монолит** с отдельным процессом Worker.

```text
                       ┌────────────────────────────┐
   Web Player ────────▶│        Persephone API       │
   Subsonic-клиенты ──▶│      (Fastify, /api/v1)     │
                       └──────────┬─────────────────┘
                                  │
          ┌───────────────────────┼────────────────────────┐
          │                       │                        │
          ▼                       ▼                        ▼
   ┌─────────────┐        ┌─────────────┐          ┌────────────────┐
   │ PostgreSQL  │        │    Redis     │          │  Интеграции    │
   │ (истина)    │        │ кэш/очереди  │          │ Navidrome      │
   └─────────────┘        └──────┬──────┘          │ Lidarr         │
                                 │                 │ MusicBrainz    │
                          ┌──────▼──────┐          │ Last.fm        │
                          │   Worker    │◀─────────┘
                          │  (BullMQ)   │
                          └─────────────┘
```

API и Worker используют общий код, общую конфигурацию и общую модель данных, но запускаются и масштабируются независимо.

Причины выбора описаны в [ADR 0001](docs/adr/0001-modular-monolith.md).

## 2. Границы компонентов

### 2.1. API

- HTTP-слой: маршруты, валидация входа, аутентификация, формирование ответа.
- Слой приложения: сценарии использования в `app/src/modules/*`.
- Бизнес-логика не размещается в HTTP-маршрутах.
- API не зависит от конкретного frontend и не возвращает внутренние пути файловой системы.

### 2.2. Worker

- Фоновые задачи BullMQ: scrobble, metadata, recommendation, prefetch.
- Задачи идемпотентны и защищены от дублирования.
- Worker не обслуживает пользовательские HTTP-запросы.
- При недоступности Redis API сохраняет работоспособность и сообщает об ограничениях.

### 2.3. Модули

`app/src/modules/` содержит прикладную логику:

| Модуль | Ответственность |
|---|---|
| `auth` | регистрация, вход, сессии, роли |
| `users` | профиль и настройки пользователя |
| `library` | каталог, storage roots, индексация, поиск |
| `playback` | сессии воспроизведения, история, scrobble-порог |
| `playlists` | плейлисты и очереди |
| `recommendations` | кандидаты, ранжирование, объяснения |
| `lastfm` | персональная привязка и синхронизация Last.fm |
| `prefetch` | прогноз и подготовка следующих композиций |

Модуль не обращается напрямую к таблицам другого модуля: взаимодействие идёт через сервисные интерфейсы.

### 2.4. Интеграции

Внешние системы изолированы адаптерами в `app/src/integrations/`:

- `navidrome` — playback backend и источник библиотеки;
- `lidarr` — управление библиотекой и импортом;
- `musicbrainz` — внешние музыкальные идентификаторы;
- `lastfm` — персональные музыкальные данные.

Контракты описаны в [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md).

Ключевое правило: **внешний сервис — адаптер, а не центральная бизнес-логика**. Отказ любого адаптера не должен останавливать воспроизведение уже имеющихся файлов.

## 3. Владение данными

PostgreSQL — источник истины для собственных сущностей Persephone Music ([ADR 0003](docs/adr/0003-postgresql-as-source-of-truth.md)):

- пользователи, сессии, настройки;
- каталог: исполнители, записи, релизы, позиции, медиафайлы;
- storage roots;
- история прослушиваний и скробблы;
- предпочтения, избранное, пропуски;
- плейлисты и очереди;
- рекомендации и prefetch-задачи.

Navidrome и Lidarr не являются хранилищем пользовательской истории Persephone и не должны становиться единственной точкой отказа.

## 4. Playback

Воспроизведение проходит через абстракцию:

```js
playbackAdapter.getStream({ userId, mediaAssetId, clientCapabilities });
```

Требования:

- отдаётся оригинальный файл (Original First, [ADR 0002](docs/adr/0002-original-first-playback.md));
- поддерживаются HTTP Range и перемотка;
- транскодирование в MVP отсутствует;
- авторизация и проверка прав выполняются до выдачи потока;
- реализация не зависит от конкретного playback backend.

## 5. Хранение файлов

- Файлы описываются через `storage_roots` + `relative_path` ([ADR 0005](docs/adr/0005-multi-storage-abstraction.md)).
- Абсолютные пути хоста не являются основой идентификации.
- `media_assets` хранит SHA256, размер, формат и технические параметры.
- Одна запись (recording) может иметь несколько файлов, в том числе в разных форматах и хранилищах.

## 6. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| Last.fm недоступен | воспроизведение продолжается, скробблы остаются в очереди |
| MusicBrainz недоступен | каталог доступен, метаданные обновляются позднее |
| Lidarr недоступен | локальная библиотека воспроизводится |
| Redis недоступен | фоновые операции приостанавливаются, API сообщает об ограничении |
| Navidrome недоступен | API сообщает о недоступности playback backend, история не повреждается |

Все фоновые операции должны быть повторяемыми и идемпотентными.

## 7. Безопасность

- Пароли — только Argon2id.
- Сессии — случайные токены, в БД хранится хеш.
- Last.fm session keys — шифрование отдельным ключом окружения.
- Проверка принадлежности пользовательских ресурсов — на каждом запросе.
- PostgreSQL и Redis не публикуются наружу.
- Административные маршруты ограничены ролью.
- Секреты не попадают в Git, логи и ответы API.

Подробности: [docs/SECURITY.md](docs/SECURITY.md).

## 8. Целевая структура кода

```text
app/src/
├── api/
│   ├── routes/
│   ├── middleware/
│   ├── app.js
│   └── server.js
├── modules/
├── integrations/
├── workers/
├── db/
│   ├── migrations/
│   └── queries/
├── services/
├── config/
└── utils/
```

Правила:

- JavaScript ESM;
- конфигурация — только через переменные окружения с валидацией;
- зависимости создаются в composition root и передаются явно;
- модули не импортируют внутренности друг друга;
- миграции БД — только в `app/src/db/migrations/` (forward-only, [ADR 0006](docs/adr/0006-forward-only-migrations.md)).

## 9. Не цели архитектуры

- Микросервисы без измеренной необходимости.
- Собственный транскодирующий движок в MVP.
- Зависимость рекомендаций исключительно от Last.fm.
- Хранение пользовательской истории исключительно в Navidrome.
- Обязательное развёртывание дубликатов Lidarr/Navidrome при наличии существующих.

## 10. Открытые вопросы

Фиксируются как Issues, а не решаются молча:

- схема сопоставления пользователей Persephone и Subsonic/Navidrome;
- поддержка нескольких артистов у одной записи;
- стратегия ротации ключа шифрования Last.fm;
- выбор frontend-стека для `web/`.
