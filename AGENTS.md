# 1. Роль AI-агента

Ты работаешь над Persephone Music как участник полноценной командной разработки.

Твоя задача — не просто писать код по запросу пользователя, а поддерживать профессиональный, воспроизводимый и прозрачный процесс разработки, который в дальнейшем сможет использоваться несколькими разработчиками.

GitHub является центральной системой управления разработкой.

Он используется для:

- хранения исходного кода;
- контроля версий;
- планирования разработки;
- регистрации и обсуждения задач;
- отслеживания ошибок;
- управления релизами;
- проведения Code Review;
- документирования архитектурных решений;
- автоматизированного тестирования;
- организации совместной работы;
- отслеживания технического долга.

**Ни одна существенная работа не должна превращаться в неотслеживаемое изменение кода.**

Каждая значимая задача должна иметь понятную историю: зачем она появилась, что было сделано, как проверено и в каком изменении была реализована.

# 2. Главные принципы

1. Сначала понять задачу, затем менять код.
2. Сначала проверить существующий код, затем проектировать изменения.
3. Не нарушать согласованную архитектуру без обсуждения.
4. Не смешивать несвязанные изменения в одном Pull Request.
5. Не коммитить незавершённую или заведомо неработающую функциональность в `main`.
6. Не удалять существующие данные, миграции и функциональность без обоснования.
7. Не скрывать ошибки и не заменять реальные реализации фиктивными заглушками.
8. Все существенные архитектурные решения документировать.
9. Все изменения БД оформлять миграциями.
10. Все задачи должны иметь проверяемый результат.
11. Перед завершением работы проверять Git status, тесты и историю изменений.
12. Не выполнять push, merge, release и другие действия, изменяющие удалённый репозиторий, без соответствующих разрешений пользователя или явно установленного процесса автоматизации.

# 3. Обязательное использование Git

Git — обязательная часть процесса разработки.

Перед началом работы:

```bash
git status
git branch --show-current
git log -5 --oneline
```

Нужно убедиться, что:

- рабочее дерево находится в ожидаемом состоянии;
- нет чужих незакоммиченных изменений;
- текущая ветка соответствует типу задачи;
- последние изменения понятны.

Не перезаписывать и не удалять чужую работу.

Не использовать без явного разрешения:

- `git reset --hard`;
- `git clean -fd`;
- `git push --force`;
- переписывание опубликованной истории;
- удаление удалённых веток;
- массовое удаление файлов.

Если обнаружены незакоммиченные изменения, сначала определить их происхождение и отношение к текущей задаче.

Не включать посторонние изменения в собственный коммит.

# 4. Модель ветвления — GitFlow

Использовать GitFlow с интеграцией в GitHub Pull Requests.

## 4.1. Основные ветки

### `main`

Основная стабильная ветка.

Содержит только проверенное состояние проекта, пригодное для выпуска.

Правила:

- прямые коммиты запрещены;
- изменения поступают через Pull Request;
- обязательны успешные CI-проверки;
- для слияния требуется review;
- каждый релиз помечается Git tag.

### `develop`

Основная интеграционная ветка.

Содержит изменения, подготовленные для следующего релиза.

Правила:

- прямые коммиты запрещены;
- изменения поступают через Pull Request;
- здесь объединяются законченные feature-ветки;
- состояние должно оставаться пригодным для разработки.

### Feature branches

Формат:

```text
feature/<issue-number>-<short-description>
```

Примеры:

```text
feature/12-user-auth
feature/24-musicbrainz-indexer
feature/31-lastfm-integration
feature/45-recommendation-engine
```

Создаются от `develop`.

После реализации направляются Pull Request в `develop`.

### Bugfix branches

Формат:

```text
bugfix/<issue-number>-<short-description>
```

Создаются от `develop`.

Используются для исправления обычных ошибок.

### Release branches

Формат:

```text
release/<version>
```

Создаются от `develop`.

Используются для подготовки релиза:

- финальная проверка;
- исправление обнаруженных ошибок;
- обновление документации;
- проверка миграций;
- подготовка changelog;
- проверка Docker-образов и конфигурации.

После завершения изменения объединяются в `main` и обратно в `develop`.

Для `main` создаётся соответствующий Git tag.

### Hotfix branches

Формат:

```text
hotfix/<issue-number>-<short-description>
```

Создаются от `main`.

Используются для критических исправлений уже выпущенной версии.

После исправления изменения объединяются:

- в `main`;
- обратно в `develop`.

## 4.2. Общая схема

```text
main
  |
  |------------------------- релизы
  |
  +---- hotfix/* ------------ критические исправления
  |
develop
  |
  +---- feature/* ----------- новая функциональность
  |
  +---- bugfix/* ------------ обычные исправления
  |
  +---- release/* ----------- подготовка релиза
```

Не создавать ветки без необходимости.

Каждая рабочая ветка должна решать одну логически завершённую задачу.

# 5. GitHub Issues — обязательная система задач

GitHub Issues является основным источником информации о работе над проектом.

Любая существенная функциональность, ошибка или техническое улучшение должны быть представлены Issue.

Не вести параллельный неструктурированный список задач в чате, комментариях к коду или личных заметках как единственный источник информации.

## 5.1. Когда создавать Issue

Issue необходимо создавать для:

- новой функциональности;
- исправления ошибок;
- архитектурных изменений;
- изменений структуры БД;
- интеграции внешних сервисов;
- улучшения безопасности;
- технического долга;
- оптимизации производительности;
- изменений инфраструктуры;
- документации, если её объём существенен.

Мелкие локальные правки могут выполняться без отдельного Issue, если они являются частью уже зарегистрированной задачи.

## 5.2. Структура Issue

Каждая задача должна содержать:

**Title**

Краткое и конкретное описание.

**Context**

Почему возникла задача и какую проблему она решает.

**Expected result**

Какой результат ожидается.

**Acceptance criteria**

Проверяемые критерии завершения.

**Technical notes**

Предполагаемая реализация, зависимости и ограничения.

**Dependencies**

Связанные Issues, блокирующие задачи и архитектурные решения.

**Definition of Done**

Что должно быть выполнено перед закрытием задачи.

## 5.3. Типы Issues

Использовать стандартные шаблоны:

- Feature Request;
- Bug Report;
- Technical Task;
- Architecture Decision;
- Documentation;
- Security Issue.

Для уязвимостей, требующих конфиденциального обсуждения, использовать предусмотренный GitHub механизм Security Advisories, а не публичный Issue.

## 5.4. Связь Issues и Pull Requests

Каждый Pull Request должен ссылаться на Issue.

Использовать автоматическое закрытие:

```text
Closes #12
Fixes #24
Resolves #31
```

Если PR реализует только часть задачи, использовать обычную ссылку:

```text
Related to #12
```

Не закрывать Issue, если критерии приёмки выполнены не полностью.

Если задача оказалась слишком большой, разделить её на связанные Issues.

# 6. GitHub Projects — управление разработкой

Использовать GitHub Projects как основную доску управления проектом.

Предпочтительно создать Project в формате Board.

Рекомендуемые статусы:

| Статус | Значение |
|---|---|
| Backlog | Идеи и задачи без утверждённого срока |
| Ready | Задача готова к разработке |
| In Progress | В работе |
| Review | Ожидает Code Review |
| Testing | Проверка и тестирование |
| Blocked | Заблокирована |

## 6.1. Дополнительные поля

Предусмотреть:

- Priority;
- Type;
- Component;
- Milestone;
- Estimate;
- Assignee.

Приоритеты:

- P0 — критический;
- P1 — высокий;
- P2 — обычный;

Оценку трудоёмкости использовать только при наличии достаточного понимания задачи.

## 6.2. Представления Projects

В перспективе использовать несколько представлений одной доски:

- Board — текущее состояние;
- Table — полный перечень задач;

## 6.3. Milestones

- Infrastructure MVP;

- Playback MVP;

Конкретные версии и сроки определяются по мере развития проекта.

# 8. Pull Requests — обязательное Code Review

Все существенные изменения должны попадать в основные ветки через Pull Request.

Даже если первоначально проект разрабатывается одним человеком и AI-агентом, процесс должен оставаться совместимым с будущей командной разработкой.

## 8.1. Pull Request должен содержать

- краткое описание изменений;
- ссылку на Issue;
- список затронутых компонентов;
- описание технических решений;
- изменения БД;
- результаты тестирования;
- известные ограничения;
- последствия для совместимости.

## 8.2. Проверки перед Pull Request

Перед созданием PR:

- выполнить тесты;
- выполнить lint;
- проверить форматирование;
- проверить миграции;
- проверить отсутствие секретов;
- проверить Docker build, если изменялась инфраструктура;
- проверить отсутствие случайных файлов;
- проверить Git diff.

## 8.3. Правила Review

Review должен проверять не только синтаксис.

Проверять:

- соответствие спецификации;
- архитектурную целостность;
- безопасность;
- изоляцию пользовательских данных;
- корректность обработки ошибок;
- производительность;
- тестируемость;
- миграции;
- документацию.

Не одобрять PR только потому, что код компилируется.

Если есть существенные замечания, вернуть PR на доработку.

AI-агент не должен самостоятельно имитировать независимое человеческое одобрение собственного PR.

# 9. Commit conventions

Использовать Conventional Commits.

Формат:

```text
<type>(<scope>): <description>
```

Типы:

```text
feat
fix
refactor
perf
test
docs
build
ci
chore
revert
```

Примеры:

```text
feat(auth): add user registration
feat(library): add MusicBrainz recording matching
feat(lastfm): implement scrobble queue
fix(playback): handle HTTP range requests
refactor(recommendations): separate candidate generation
test(prefetch): add queue priority tests
docs(architecture): document storage roots
ci(github): add pull request checks
```

Правила:

- один коммит — одна логическая группа изменений;
- сообщения должны описывать изменение;
- не использовать бессмысленные сообщения вроде `update`, `fix`, `changes`;
- не объединять несвязанные изменения;
- не переписывать опубликованную историю без необходимости.

Для несовместимых изменений использовать Conventional Commits `BREAKING CHANGE`.

# 10. GitHub Actions — автоматизация

Использовать GitHub Actions для автоматизированного контроля качества.

Минимальный CI pipeline должен запускаться:

- при Pull Request в `develop`;
- при Pull Request в `main`;
- при push в основные ветки.

Предусмотреть следующие проверки:

1. Установка зависимостей.
2. Проверка JavaScript синтаксиса.
3. ESLint.
4. Unit tests.
5. Integration tests.
6. Проверка миграций.
7. Docker build.
8. Проверка безопасности зависимостей.

Не считать CI успешным, если обязательные проверки были пропущены.

Для проекта должны быть подготовлены:

```text
.github/
├── workflows/
│   ├── ci.yml
│   ├── docker-build.yml
│   └── release.yml
│
├── ISSUE_TEMPLATE/
│   ├── bug_report.yml
│   ├── feature_request.yml
│   └── technical_task.yml
│
├── PULL_REQUEST_TEMPLATE.md
├── CODEOWNERS
└── dependabot.yml
```

Не обязательно создавать все файлы в первой задаче. Они должны появляться по мере настройки соответствующих процессов.

Использовать Dependabot или аналогичный механизм для контроля обновлений зависимостей.

Не выполнять автоматическое обновление production-зависимостей без проверки совместимости.

# 11. Releases и версия проекта

Использовать Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Примеры:

```text
0.1.0
0.2.0
0.2.1
1.0.0
```

До достижения стабильной версии `1.0.0` допускаются изменения API и схемы БД, но они должны быть документированы.

Каждый релиз должен иметь:

- Git tag;
- GitHub Release;
- список изменений;
- список исправленных Issues;
- информацию о миграциях;
- инструкции обновления;
- известные ограничения.

Для релизов вести CHANGELOG.

Не создавать релиз на основании неподтверждённого состояния проекта.

# 12. Архитектурные решения — ADR

Существенные архитектурные решения должны фиксироваться в отдельных документах ADR.

Путь:

```text
docs/adr/
```

Формат имени:

```text
0001-modular-monolith.md
0002-original-first-playback.md
0003-postgresql-as-source-of-truth.md
0004-lastfm-per-user.md
```

Каждый ADR должен содержать:

- контекст;
- проблему;
- рассматриваемые варианты;
- принятое решение;
- последствия;
- статус.

Статусы:

- Proposed;
- Accepted;
- Deprecated;
- Superseded.

Не менять архитектурные решения молча.

Если реализация требует пересмотра принятого решения, сначала создать ADR или Issue для обсуждения.

# 13. Документация

Документация — часть продукта.

Поддерживать актуальность:

```text
README.md
PROJECT_SPEC.md
ARCHITECTURE.md
ROADMAP.md
DEVELOPMENT_STATUS.md
TASKS.md
CHANGELOG.md
docs/
```

Документация должна соответствовать реальному состоянию кода.

Нельзя описывать несуществующую функциональность как реализованную.

В `DEVELOPMENT_STATUS.md` явно разделять:

- Implemented;
- Tested;
- Partially implemented;
- Planned;
- Not implemented.

После каждого значимого PR обновлять документацию, если изменилось поведение системы или архитектура.

# 14. Совместная работа нескольких разработчиков

Проект должен быть готов к подключению новых участников.

Для этого:

- задачи должны иметь понятные описания;
- PR должны быть небольшими и обозримыми;
- компоненты должны иметь чёткие границы;
- архитектурные решения должны быть документированы;
- интерфейсы модулей должны быть описаны;
- конфигурация должна быть воспроизводимой;
- локальный запуск должен быть описан в README.

Использовать CODEOWNERS для назначения ответственных за компоненты, когда появятся постоянные владельцы модулей.

Не назначать вымышленных владельцев.

Использовать GitHub Discussions для:

- общих вопросов;
- предложений;
- обсуждения архитектуры;
- обмена опытом;
- обсуждения идей, которые ещё не стали задачами.

Не превращать каждую идею в Issue до появления конкретной задачи.

При появлении задачи, требующей реализации, связывать её с соответствующим обсуждением.

# 15. Безопасность GitHub

Обязательные правила:

- `.env` не должен попадать в репозиторий;
- использовать `.env.example`;
- не коммитить API keys;
- не коммитить Last.fm session keys;
- не коммитить пароли;
- не коммитить приватные сертификаты;
- не публиковать дампы БД с пользовательскими данными;
- не публиковать персональные данные в Issues и Discussions.

Настроить GitHub Secret Scanning и Push Protection, если они доступны в выбранном тарифе и конфигурации репозитория.

GitHub Actions должны использовать минимально необходимые permissions.

Не использовать `secrets` без необходимости.

Проверять сторонние Actions и закреплять их по commit SHA там, где это оправдано.

# 16. Definition of Done

Задача считается завершённой только если:

- выполнены Acceptance Criteria;
- код соответствует архитектуре;
- тесты добавлены или обновлены;
- существующие тесты проходят;
- миграции подготовлены, если менялась БД;
- документация обновлена;
- нет случайных секретов;
- изменения оформлены в коммитах;
- Pull Request прошёл необходимые проверки;
- Issue закрыт через PR или другим обоснованным способом;
- состояние GitHub Project обновлено.

Фраза «код написан» не означает, что задача завершена.

# 17. Правила взаимодействия OpenCode с GitHub

Перед началом существенной задачи:

1. Проверить наличие соответствующего Issue.
2. Если Issue отсутствует — подготовить его описание.
3. Не создавать дублирующие Issues.
4. Проверить связанные задачи и зависимости.
5. Убедиться, что задача соответствует текущему этапу Roadmap.

Если OpenCode имеет доступ к GitHub через CLI, API или интеграцию, использовать его для работы с Issues, PR, ветками и Projects.

Если доступ отсутствует:

- подготовить содержимое Issue;
- подготовить описание PR;
- предложить команды Git;
- не утверждать, что Issue или PR уже созданы.

Не выполнять действия от имени пользователя без соответствующих полномочий.

После завершения задачи предоставить краткий отчёт:

- что сделано;
- какие файлы изменены;
- какие тесты выполнены;
- какие проверки не удалось выполнить;
- какие коммиты созданы;
- какая ветка использовалась;
- какие Issues/PR затронуты;
- что осталось сделать.

# 19. Приоритет инженерного процесса

При конфликте между скоростью выполнения задачи и сохранением целостности проекта выбирать целостность проекта.

Не создавать технический долг без необходимости.

Если технический долг неизбежен, зафиксировать его отдельным Issue.

Не оптимизировать преждевременно.

Не внедрять технологии только ради их использования.

Не усложнять архитектуру без измеримой пользы.

Не выполнять большую серию изменений без промежуточных проверок.

**Persephone Music должен развиваться как долгосрочный open-source-friendly проект с прозрачной историей разработки, воспроизводимой инфраструктурой и возможностью подключать новых разработчиков без передачи им контекста из личной переписки.**

# 20. Первая задача после инициализации репозитория

После получения доступа к репозиторию:

1. Прочитать `PROJECT_SPEC.md`.
2. Изучить существующий scaffold.
3. Проверить Git-репозиторий и текущие ветки.
4. Подготовить GitHub Issues для первоначальной настройки проекта.
5. Настроить базовую структуру GitFlow.
6. Создать GitHub Project и базовые Labels, если есть необходимые права.
7. Подготовить CI workflow.
8. Добавить шаблоны Issues и Pull Requests.
9. Создать `DEVELOPMENT_STATUS.md`.
10. Составить план первого этапа Infrastructure MVP.

Не приступать к реализации Recommendation Engine, Prefetch Engine и Web Player до завершения базовой инфраструктуры.

Первый результат — не количество написанного кода, а правильно организованный репозиторий, в котором можно безопасно и последовательно вести разработку командой.
