## 1. Модель угроз (кратко)

| Угроза | Последствие | Меры |
|---|---|---|
| Компрометация пароля | доступ к чужому профилю | Argon2id, ограничение попыток, HTTPS |
| Кража токена сессии | доступ к аккаунту | случайные токены, хеш в БД, срок жизни, отзыв |
| Утечка Last.fm session key | доступ к чужому Last.fm | шифрование отдельным ключом, запрет логирования |
| IDOR (доступ к чужому ресурсу) | утечка истории/плейлистов | проверка `user_id` на каждом запросе |
| Утечка секретов через Git | компрометация интеграций | `.gitignore`, secret scanning, `.env.example` |
| Открытые наружу БД/Redis | прямой доступ к данным | закрытые порты, внутренняя сеть Docker |
| Подмена/повреждение файлов | некорректное воспроизведение | SHA256, проверка размера и статуса |
| Path traversal | доступ к файлам вне хранилища | `relative_path` + нормализация + проверка root |
| SSRF через URL интеграций | доступ к внутренней сети | фиксированные base URL из конфигурации |
| Отказ внешнего сервиса | деградация | изоляция адаптеров, очереди, таймауты |

## 2. Аутентификация

- Пароли хранятся только как **Argon2id**-хеши с индивидуальной солью и параметрами, зафиксированными в конфигурации.
- Пароли в открытом виде не логируются, не возвращаются API и не попадают в аналитику.
- Регистрация и вход — только по HTTPS (или через доверенный reverse proxy).
- Ограничение частоты попыток входа и сброса пароля.
- Сообщения об ошибке входа не раскрывают, существует ли аккаунт.
- Роли: `admin`, `user`. Повышение прав — только администратором.
- Административные маршруты (`/api/v1/admin`) требуют роль `admin` и дополнительно ограничиваются на уровне reverse proxy, если возможно.

## 3. Сессии и токены

- Токен сессии — криптографически случайное значение (не менее 256 бит).
- В БД хранится только хеш токена (`user_sessions.token_hash`).
- Срок жизни сессии ограничен; предусмотрены продление и явный отзыв.
- При смене пароля и отвязке аккаунта все активные сессии пользователя отзываются.
- Cookie (если используются) — `HttpOnly`, `Secure`, `SameSite=Lax` или строже.
- Если используется Bearer-токен, он не попадает в URL и логи.

## 4. Авторизация

- Каждый пользовательский ресурс проверяется на принадлежность `userId` из сессии.
- Идентификатор пользователя никогда не берётся из тела запроса для определения владельца.
- Списки (плейлисты, история, очередь, рекомендации) фильтруются по `user_id` на уровне запроса к БД.
- Публичные плейлисты, если появятся, требуют отдельного явного флага и не раскрывают другие данные.
- Ошибка доступа возвращает `404` или `403` без раскрытия существования чужого ресурса.

## 5. Секреты и конфигурация

- Все секреты — только через переменные окружения.
- `.env` исключён из Git; в репозитории только `.env.example` с заглушками.
- Секреты не логируются и не возвращаются в ответах API.
- Обязательные переменные валидируются при старте; при отсутствии процесс завершается с ошибкой.
- `SECRET_ENCRYPTION_KEY` — отдельный ключ для шифрования Last.fm session keys (32 байта, base64).
- `SESSION_SECRET` не должен совпадать с ключом шифрования.
- Ротация ключей должна быть задокументирована до production-использования.

Реализовано в Stage 0:

- `app/src/config/index.js` валидирует обязательные переменные, протоколы URL, диапазоны и длину секретов;
- ошибки конфигурации содержат имена переменных, но не их значения;
- `describeConfig()` не включает секреты;
- pino настроен на redaction паролей, токенов, cookie и ключей;
- Last.fm session keys шифруются AES-256-GCM в формате `[formatVersion][keyVersion][iv:12][authTag:16][ciphertext]`.

Запрещено коммитить:

- API-ключи Last.fm, Lidarr, Navidrome;
- пароли и session keys;
- приватные сертификаты и ключи;
- дампы БД с пользовательскими данными;
- реальные `.env`-файлы.

## 6. Шифрование пользовательских данных

Last.fm session key:

- шифруется алгоритмом AES-256-GCM (или эквивалентным аутентифицированным шифрованием);
- хранится как `bytea` вместе с версией ключа и nonce/tag;
- расшифровывается только в памяти процесса, непосредственно перед вызовом Last.fm;
- никогда не передаётся клиенту;
- удаляется при отвязке аккаунта.

Реализация Stage 0: `app/src/utils/secrets.js` (`encryptSecret`, `decryptSecret`, `readSecretKeyVersion`). Ключ и его версия передаются отдельно; поле `user_lastfm.encryption_key_version` хранит версию, необходимую для ротации.

Персональные данные в открытом виде (email, история) защищаются средствами БД и доступом, а не шифрованием на уровне приложения, если не появится отдельное требование.

## 7. Сетевая безопасность

- PostgreSQL и Redis не публикуют порты на хост в базовой конфигурации.
- Для локальной разработки допускается публикация только на `127.0.0.1` через отдельный override.
- Navidrome и Lidarr не открываются в интернет без reverse proxy и дополнительной защиты.

Реализовано в Stage 0: базовый `docker-compose.yml` не публикует порты PostgreSQL/Redis; `docker-compose.dev.yml` привязывает их к `127.0.0.1`; Navidrome и Lidarr опубликованы только на `127.0.0.1`.
- API доступен через HTTPS; TLS завершается на reverse proxy.
- Внутренние сервисы общаются по внутренней сети Docker.
- CORS ограничен известными origin; wildcard в production запрещён.
- Заголовки безопасности: `Strict-Transport-Security`, `X-Content-Type-Options`, `Content-Security-Policy` для Web Player.

## 8. Работа с файлами

- Клиенту не возвращаются абсолютные пути.
- `relative_path` нормализуется; выход за пределы storage root запрещён.
- Проверка прав выполняется до выдачи потока.
- Поток отдаётся только для `media_assets.status = 'available'`.
- SHA256 и размер используются для целостности и дедупликации.
- MIME-тип определяется по фактическому формату, а не по расширению из запроса.

## 9. Логирование и аудит

Логируются:

- вход, выход, неудачные попытки входа;
- изменение пароля и привязка/отвязка Last.fm;
- административные операции;
- ошибки интеграций без секретов;
- отказы в доступе.

Не логируются:

- пароли, session keys, токены, cookies;
- полные тела запросов с чувствительными данными;
- содержимое музыкальных файлов.

Формат логов — структурированный JSON. Request ID связывает записи одного запроса.

## 10. Зависимости и CI

- Dependabot отслеживает npm, Docker и GitHub Actions.
- Обновления production-зависимостей проверяются на совместимость вручную.
- CI использует минимальные `permissions`.
- Сторонние GitHub Actions закрепляются по SHA там, где это оправдано.
- Секреты CI не используются без необходимости.
- GitHub Secret Scanning и Push Protection включаются, если доступны на тарифе.

## 11. Резервное копирование

- PostgreSQL — регулярные проверенные бэкапы.
- Ключ шифрования Last.fm — отдельное защищённое хранение; без него session keys невосстановимы.
- Музыкальные файлы — согласно политике владельца инфраструктуры.
- Восстановление из бэкапа должно быть проверено, а не только настроено.
