# ADR 0001 — Модульный монолит с отдельным Worker

- **Статус:** Accepted
- **Дата:** 2026-10-31
- **Контекст проекта:** Stage 0

## Контекст

Persephone Music объединяет API, музыкальный каталог, интеграции, рекомендации и фоновые задачи. Проект развивается небольшой командой, разворачивается самостоятельно и должен оставаться понятным новым участникам.

## Проблема

Как организовать backend, чтобы компоненты были изолированы, но инфраструктура не стала преждевременно сложной?

## Рассмотренные варианты

1. **Микросервисы** — отдельные сервисы для каталога, рекомендаций, Last.fm, prefetch.
2. **Единый монолит** — API и фоновые задачи в одном процессе.
3. **Модульный монолит + отдельный Worker** — общий код, разные процессы.

## Решение

Принят вариант 3.

- API и Worker используют общий код и общую бизнес-логику.
- API и Worker запускаются отдельными контейнерами.
- Модули имеют явные границы и не импортируют внутренности друг друга.
- Интеграции изолированы адаптерами.
- Фоновые задачи выполняются через BullMQ.

## Последствия

Положительные:

- одна кодовая база и одна модель данных;
- простое локальное развёртывание;
- Worker можно масштабировать отдельно;
- путь к выделению сервиса позже остаётся открытым.

Отрицательные:

- требуется дисциплина границ модулей;
- общий релизный цикл;
- риск «монолита без модулей» при нарушении правил.

## Ограничения

Выделение отдельного сервиса допускается только при измеряемой необходимости и после нового ADR.
