# ADR 0006 — Forward-only миграции с проверкой в CI

- **Статус:** Accepted
- **Дата:** 2026-10-31
- **Контекст проекта:** Stage 0

## Контекст

Схема БД будет развиваться на протяжении всех этапов. Нужна предсказуемая стратегия миграций, совместимая с командной разработкой и production-развёртыванием.

## Проблема

Как применять изменения схемы: с down-миграциями, forward-only или через автоматический diff?

## Рассмотренные варианты

1. **Up/down миграции** — гибко, но down-скрипты часто неверны и создают ложное чувство безопасности.
2. **Автоматический diff схемы** — удобно, но рискованно и непрозрачно.
3. **Forward-only SQL-миграции с таблицей учёта** — явно, воспроизводимо, проверяемо.

## Решение

Принят вариант 3.

- Миграции — SQL-файлы `NNNN_description.sql` в `app/src/db/migrations/`.
- Каждая миграция применяется в транзакции.
- Учёт: `schema_migrations(version, name, applied_at, checksum)`.
- Порядок детерминирован по номеру.
- Откат — компенсирующей миграцией, а не down-скриптом.
- Разрушительные изменения требуют Issue и плана переноса данных.
- Миграции проверяются на пустой PostgreSQL в CI.

## Последствия

Положительные:

- прозрачная история изменений;
- одинаковый результат на всех окружениях;
- проверка в CI;
- нет иллюзии безопасного отката.

Отрицательные:

- исправление ошибки требует новой миграции;
- разработчик обязан думать о совместимости вперёд;
- откат данных — отдельная операция.

## Ограничения

Изменение уже применённой миграции запрещено. Исправление — только новой миграцией.
