# Prefetch Engine

**Проект:** Persephone Music
**Статус:** проектирование; реализация — Stage 6
**Связанные документы:** [PROJECT_SPEC.md](../PROJECT_SPEC.md), [docs/DATA_MODEL.md](DATA_MODEL.md), [docs/RECOMMENDATION_ENGINE.md](RECOMMENDATION_ENGINE.md)

---

## 1. Назначение

Prefetch Engine предсказывает, какая музыка понадобится пользователю в ближайшее время, и заранее готовит её к воспроизведению. Он превращает рекомендации в готовые к прослушиванию композиции.

## 2. Входные данные

Для каждого пользователя анализируются:

- текущая композиция;
- очередь воспроизведения;
- активная рекомендательная выдача;
- история прослушиваний;
- последовательности прослушивания;
- контекст радио;
- явные действия (добавление в плейлист, запрос).

## 3. Прогноз

- Горизонт: следующие 3–5 композиций.
- Прогноз обновляется при изменении очереди, текущей композиции или контекста радио.
- Приоритет выше у композиций, которые с большой вероятностью будут следующими.
- Прогноз не является гарантией воспроизведения и не резервирует файлы навсегда.

## 4. Проверка доступности

Для каждой композиции последовательно проверяется:

1. Есть ли запись в каталоге (`recordings`)?
2. Есть ли доступный оригинальный файл (`media_assets.status = 'available'`)?
3. Доступен ли файл для playback (storage root активен, файл читается)?
4. Если файла нет — существует ли задача его получения?
5. Не выполняется ли такая задача уже для другого пользователя?

Только после этих проверок создаётся или переиспользуется задача.

## 5. Общие задачи

Если несколько пользователей хотят одну и ту же отсутствующую композицию:

- создаётся **одна** задача `prefetch_jobs` на запись;
- причины и приоритеты хранятся отдельно в `prefetch_job_requests`;
- один пользователь может добавить несколько причин (радио, плейлист, рекомендация);
- при отмене интереса одного пользователя задача не отменяется, пока есть другие запросы;
- при исчезновении всех запросов задача может быть отменена.

Пример:

- пользователь A хочет композицию для радио;
- пользователь B добавил её в плейлист;
- пользователь C получил её в рекомендациях.

Все три запроса ссылаются на одну общую задачу.

## 6. Приоритет

Приоритет задачи зависит от:

- близости воспроизведения (следующая композиция > через 5 треков);
- наличия в текущей очереди;
- количества заинтересованных пользователей;
- вероятности прослушивания;
- доступности и стоимости получения контента.

Формула — конфигурируемая эвристика. Пример:

```text
priority = w1 * proximity
         + w2 * queue_presence
         + w3 * interested_users
         + w4 * play_probability
         - w5 * estimated_cost
```

Веса калибруются; значения не хардкодятся в бизнес-логике.

## 7. Ограничения ресурсов

Предусмотреть:

- ограничение числа параллельных задач;
- ограничение скорости запросов к источникам;
- контроль свободного места;
- максимальное число попыток;
- экспоненциальную задержку между попытками;
- отмену устаревших задач;
- понижение приоритета давно ожидающих задач;
- журналирование каждого перехода статуса.

## 8. Жизненный цикл задачи

```text
pending → queued → running → completed
                    ↓
                  failed → (retry) → queued
                    ↓
                cancelled
```

Правила:

- одна активная задача на запись (частичный уникальный индекс);
- повторные попытки ограничены `max_attempts`;
- ошибка не удаляет задачу и не теряет пользовательские запросы;
- завершённая задача сохраняется для аудита и дедупликации;
- отмена — мягкая (`status = 'cancelled'`).

## 9. Источники контента

- Получение отсутствующей музыки выполняется через настраиваемые адаптеры разрешённых источников.
- Архитектура не привязывается к конкретному загрузчику.
- Lidarr может выступать менеджером импорта.
- Наличие протокола или торрента не подтверждает правомерность распространения контента.
- Ответственность за источники и права — на владельце инфраструктуры.

## 10. Наблюдаемость

Метрики:

- размер очереди по статусам;
- время от запроса до готовности;
- доля успешных задач;
- количество общих задач с несколькими пользователями;
- отменённые и устаревшие задачи;
- использование диска.

Логи:

- создание задачи и причина;
- смена статуса;
- ошибки с классификацией;
- отмена с причиной.

## 11. Взаимодействие с Recommendation Engine

- Рекомендация может порождать prefetch-запрос, но не обязана.
- Если файла нет, рекомендация помечается как требующая подготовки.
- Prefetch не изменяет ранжирование рекомендаций напрямую.
- Готовность файла может повысить приоритет показа рекомендации.

## 12. Ограничения MVP

- Нет гарантии получения контента.
- Нет сложного прогноза на ML.
- Один источник контента на старте.
- Ограниченный горизонт прогноза.

## 13. Открытые вопросы

1. Политика хранения завершённых задач.
2. Квоты на пользователя и на систему.
3. Поведение при заполнении диска.
4. Согласование с внешним Lidarr, если он уже управляет очередью.
5. Метрика «вероятность прослушивания» и её обучение.
