## Единая концепция и техническая спецификация проекта

**Версия документа:** 0.2  
**Статус:** проектирование / подготовка к разработке  
**Назначение:** основной документ для разработки проекта с помощью OpenCode.

# 1. Общая концепция

Persephone Music — собственная многопользовательская музыкальная платформа, объединяющая функции музыкального стримингового сервиса, персонального музыкального дневника, рекомендательной системы и интеллектуального управления музыкальной библиотекой.

По пользовательскому опыту проект ориентируется на Spotify, Яндекс Музыку и Last.fm, но должен работать на собственной инфраструктуре и использовать собственную библиотеку музыкальных файлов.

Основная идея:

- Одна общая физическая музыкальная библиотека.
- Несколько независимых пользователей.
- Индивидуальная история прослушиваний.
- Индивидуальные предпочтения и рекомендации.
- Персональные интеграции с Last.fm.
- Собственный Recommendation Engine.
- Интеллектуальная система предварительной подготовки музыки (Prefetch Engine).
- Собственный Web Player.
- Поддержка сторонних клиентов через Subsonic API.

Проект должен быть модульным, расширяемым и пригодным для самостоятельного размещения на сервере.

Это не попытка сделать очередную обёртку над Navidrome. Navidrome и Lidarr выступают инфраструктурными компонентами, а логика персонализации, рекомендаций, пользовательских профилей и предсказания прослушивания принадлежит Persephone Music.

# 2. Основные принципы

## 2.1. Общая библиотека, независимые пользователи

Физические музыкальные файлы хранятся в общей библиотеке.

При этом каждый пользователь имеет собственное независимое пространство данных:

- история прослушиваний;
- любимые композиции;
- оценки и предпочтения;
- история пропусков;
- плейлисты;
- очередь воспроизведения;
- рекомендации;
- музыкальные интересы;
- настройки качества и воспроизведения;
- аккаунт Last.fm;
- персональная статистика.

Действия одного пользователя не должны автоматически изменять музыкальные предпочтения другого.

Если пользователь инициировал добавление отсутствующей композиции, после её появления в общей библиотеке она становится технически доступна всем. Однако это не означает, что она автоматически попадёт в рекомендации всех пользователей.

## 2.2. Разделение сущностей

Необходимо строго разделять:

1. Музыкального исполнителя.
2. Музыкальное произведение (Recording).
3. Релиз (альбом, сингл, сборник, переиздание).
4. Позицию произведения на конкретном релизе.
5. Физический медиафайл.
6. Пользовательские предпочтения относительно произведения.

Одна запись может присутствовать на нескольких релизах.

Одна запись может иметь несколько физических файлов, например FLAC и MP3.

Нельзя считать музыкальную композицию и файл одной сущностью.

## 2.3. Собственная логика платформы

Persephone Music должна владеть собственными данными и логикой.

Нельзя строить архитектуру таким образом, чтобы:

- рекомендации зависели исключительно от Last.fm;
- пользовательская история хранилась исключительно в Navidrome;
- идентификация композиций зависела исключительно от Lidarr;
- отсутствие внешнего сервиса останавливало воспроизведение уже имеющейся музыки.

Внешние сервисы — адаптеры и источники данных, а не центральная бизнес-логика.

# 3. Пользовательская модель

Платформа многопользовательская.

Для каждого пользователя создаётся отдельный профиль.

Предусмотреть:

- регистрацию и авторизацию;
- управление сессиями;
- индивидуальные настройки;
- привязку собственного Last.fm;
- историю прослушиваний;
- пользовательские плейлисты;
- избранное;
- исключения и нежелательные композиции;
- персональное радио;
- рекомендации;
- персональную статистику.

В перспективе предусмотреть роли:

- Administrator;
- User.

Администратор управляет инфраструктурой и общей библиотекой.

Пользователь управляет только собственным профилем и пользовательскими данными, если ему явно не выданы дополнительные права.

# 4. Музыкальная библиотека

## 4.1. Источник истины

PostgreSQL является источником истины для собственных сущностей Persephone Music.

Физические файлы могут управляться через Lidarr и находиться в файловой системе или на сетевых хранилищах.

Navidrome используется как начальный playback backend и индексатор/сервер библиотеки в рамках своих возможностей.

## 4.2. Метаданные

Основной внешний источник музыкальных идентификаторов — MusicBrainz.

Использовать:

- MusicBrainz Artist ID;
- MusicBrainz Recording ID;
- MusicBrainz Release ID;
- MusicBrainz Release Group ID, если применимо.

Внутренние идентификаторы Persephone должны оставаться самостоятельными.

Внешние идентификаторы не должны быть первичными ключами внутренних таблиц.

Для идентификации файлов использовать:

- SHA256;
- размер файла;
- формат;
- длительность;
- технические параметры;
- относительный путь;
- storage root.

Необходимо предусмотреть ручное исправление и объединение ошибочно распознанных музыкальных сущностей.

## 4.3. Хранилища

В первой версии допускается одно основное хранилище.

Архитектура БД должна сразу предусматривать несколько хранилищ.

Сущность `storage_roots` должна содержать:

- внутренний ID;
- название;
- тип хранилища;
- внутренний идентификатор или mount point;
- статус;
- дату добавления.

В `media_assets` хранить:

- `storage_root_id`;
- `relative_path`.

Не сохранять абсолютные пути хоста как основу идентификации файла.

В будущем необходимо поддержать:

- несколько локальных дисков;
- сетевые файловые системы;
- отдельные хранилища для разных типов контента;
- перемещение файлов между хранилищами без изменения идентичности музыкальной записи.

Отдельно проверить поддержку нескольких музыкальных корней Navidrome. Не предполагать, что он автоматически поддерживает любую будущую схему хранения.

# 5. Качество и воспроизведение

## 5.1. MVP — Original First

На первом этапе платформа передаёт оригинальные музыкальные файлы без изменения качества.

Транскодирование в MVP не используется.

Требования:

- отдавать исходный файл;
- поддерживать HTTP Range;
- поддерживать перемотку;
- не изменять аудиоданные;
- учитывать поддержку форматов клиентом;
- не создавать производные версии файлов.

Формат и качество определяются исходным файлом и возможностями клиента.

## 5.2. Будущее развитие

В дальнейшем добавить необязательное транскодирование.

Планируемые режимы:

- Original — оригинальный файл;
- Auto — автоматический выбор качества;
- Custom — пользовательские ограничения;
- Always transcode — принудительное преобразование.

Транскодирование не должно менять или перезаписывать оригинальные файлы.

Производные версии могут храниться во временном кэше.

В таблице пользовательских настроек заранее предусмотреть:

- `preferred_format`;
- `max_bitrate_kbps`;
- `transcode_policy`.

В MVP допустимо только значение `source` для политики качества. Не реализовывать фиктивные режимы, которые фактически не работают.

## 5.3. Playback Adapter

Воспроизведение должно проходить через абстракцию:

`playbackAdapter.getStream({ userId, mediaAssetId, clientCapabilities })`

Реализация должна быть независимой от конкретного playback backend.

В будущем это позволит менять Navidrome или использовать другой сервер, не переписывая пользовательскую логику.

Важно: HTTP Range, авторизация и корректная обработка потоков должны быть реализованы и проверены отдельно. Нельзя считать их автоматически обеспеченными одной только схемой БД.

# 6. Last.fm

Last.fm — важная интеграция, но не центральная зависимость проекта.

У каждого пользователя собственный Last.fm аккаунт.

Общий API key приложения используется для интеграции, но пользовательские session keys должны храниться отдельно.

Предусмотреть:

### Исходящие операции

- `track.updateNowPlaying`;
- `track.scrobble`;
- `track.love` — если операция доступна и пользователь включил соответствующую синхронизацию.

### Входящие данные

Использовать доступные методы Last.fm для получения:

- похожих исполнителей;
- похожих композиций;
- любимых треков;
- любимых исполнителей;
- истории прослушивания;
- популярных треков и исполнителей;
- тегов и жанровых характеристик.

Конкретный набор методов определить при реализации адаптера с учётом актуальной документации Last.fm API.

### Требования

- Last.fm подключается независимо для каждого пользователя.
- Сбой Last.fm не должен останавливать воспроизведение.
- Скробблинг выполняется через очередь.
- Предусмотреть повторные попытки.
- Предусмотреть защиту от дублирования событий.
- Учитывать правила Last.fm относительно времени прослушивания и условий скробблинга.
- Хранить статус синхронизации.
- Не передавать чужие пользовательские данные между аккаунтами.

Секреты и session keys должны храниться в зашифрованном виде. Ключ шифрования приложения должен быть отдельным секретом окружения.

# 7. Recommendation Engine

Это один из главных собственных компонентов проекта.

Система должна самостоятельно формировать рекомендации, используя совокупность данных.

Не ограничиваться простым запросом похожих исполнителей в Last.fm.

## 7.1. Источники данных

- История прослушиваний Persephone.
- Повторные прослушивания.
- Любимые композиции.
- Пропуски.
- Время прослушивания.
- Последовательность композиций.
- Предпочтения исполнителей.
- Предпочтения жанров и тегов.
- Last.fm.
- MusicBrainz.
- История взаимодействия с рекомендациями.

## 7.2. Логика рекомендаций

Система должна учитывать:

- любимых исполнителей;
- похожих исполнителей;
- похожие композиции;
- жанровые связи;
- новизну;
- разнообразие;
- недавние прослушивания;
- слишком частые повторы;
- пользовательские исключения.

Необходимо разделить:

1. Candidate Generation — генерация возможных кандидатов.
2. Candidate Filtering — исключение нежелательных вариантов.
3. Ranking — ранжирование.
4. Diversity — обеспечение разнообразия.
5. Feedback — учёт реакции пользователя.

## 7.3. Объяснимость

По возможности рекомендация должна иметь объяснение:

- похож на любимого исполнителя;
- связан с недавно прослушанным альбомом;
- найден через Last.fm;
- соответствует любимому жанру;
- давно не звучал, но ранее нравился.

Рекомендации всегда персональные.

Одна и та же композиция может быть приоритетной для одного пользователя и совершенно неинтересной другому.

## 7.4. Радио

В перспективе реализовать:

- радио исполнителя;
- радио композиции;
- радио альбома;
- персональное радио;
- радио по жанру;
- радио по пользовательскому плейлисту.

Радио должно формировать последовательность композиций динамически, а не просто выдавать статический список похожих треков.

# 8. Prefetch Engine

Отдельный компонент, который предсказывает, какая музыка понадобится пользователю в ближайшее время.

Задача — заранее подготовить композиции для воспроизведения.

## 8.1. Принцип работы

Для каждого пользователя анализировать:

- текущую композицию;
- очередь воспроизведения;
- рекомендации;
- историю;
- последовательности прослушивания;
- контекст радио.

Формировать прогноз следующих 3–5 композиций.

Для каждой композиции проверять:

1. Есть ли запись в каталоге?
2. Есть ли доступный оригинальный файл?
3. Доступен ли файл для playback?
4. Если файла нет — существует ли задача его получения?
5. Не выполняется ли такая задача уже для другого пользователя?

## 8.2. Общие задачи

Если несколько пользователей хотят одну и ту же отсутствующую композицию, должна создаваться одна общая задача получения контента.

При этом приоритеты и причины запроса хранятся отдельно для пользователей.

Например:

- пользователь A хочет композицию для радио;
- пользователь B добавил её в плейлист;
- пользователь C получил её в рекомендациях.

Все три запроса могут ссылаться на одну общую задачу.

## 8.3. Приоритеты

Приоритет должен зависеть от:

- близости воспроизведения;
- наличия композиции в текущей очереди;
- количества заинтересованных пользователей;
- вероятности прослушивания;
- доступности и стоимости получения контента.

Предусмотреть:

- понижение приоритета устаревших задач;
- отмену ненужных задач;
- ограничение параллельных операций;
- ограничение скорости;
- контроль свободного места;
- журналирование.

## 8.4. Источники контента

Получение отсутствующей музыки должно выполняться через настраиваемые адаптеры разрешённых источников.

Не привязывать архитектуру к конкретному загрузчику.

Lidarr может выступать менеджером импорта и взаимодействия с библиотекой.

Нельзя считать сам факт наличия torrent или другого протокола подтверждением правомерности распространения контента.

# 9. Плейлисты и очереди

Пользователь должен иметь возможность:

- создавать плейлисты;
- переименовывать их;
- менять порядок композиций;
- удалять композиции;
- добавлять альбомы и исполнителей;
- создавать плейлисты на основе рекомендаций;
- создавать радиостанции.

Очередь воспроизведения независима для каждого пользователя.

Предусмотреть:

- текущую композицию;
- следующую композицию;
- перемешивание;
- повтор одной композиции;
- повтор очереди;
- ручное изменение порядка;
- динамическое пополнение очереди радио.

Плейлисты и очередь не должны зависеть от Navidrome как от единственного хранилища.

# 10. Технический стек

Предлагаемый базовый стек:

| Компонент | Технология |
|---|---|
| Backend | Node.js |
| Язык | JavaScript, ESM |
| HTTP API | Fastify |
| База данных | PostgreSQL |
| Очереди и кэш | Redis |
| Фоновые задачи | BullMQ |
| Playback | Navidrome |
| Управление библиотекой | Lidarr |
| Метаданные | MusicBrainz |
| Персональные музыкальные данные | Last.fm |
| Контейнеризация | Docker Compose |
| Web UI | отдельный frontend-проект |

Не переходить на микросервисы без реальной необходимости.

Начальная архитектура — модульный монолит с отдельным процессом Worker.

API и Worker могут использовать общий код и общую бизнес-логику, но запускаться как отдельные контейнеры.

Собственный Web Player и Subsonic API должны использовать общую музыкальную библиотеку, но не обязаны иметь одинаковую реализацию авторизации.

У пользователя может уже существовать ARR-инфраструктура. Поэтому при реализации нужно предусмотреть возможность подключить существующие Lidarr/Navidrome вместо обязательного развёртывания дубликатов.

# 17. Обработка ошибок и отказоустойчивость

Платформа должна продолжать работать при недоступности внешних сервисов.

Примеры:

- Last.fm недоступен — воспроизведение продолжается, скробблы остаются в очереди.
- MusicBrainz недоступен — каталог остаётся доступным, метаданные обновляются позднее.
- Lidarr недоступен — локальная библиотека продолжает воспроизводиться.
- Redis недоступен — фоновые операции могут временно приостановиться, но API должен корректно сообщить об ограничениях.
- Navidrome недоступен — API сообщает о недоступности playback backend, не повреждая пользовательскую историю.

Все фоновые операции должны быть повторяемыми и защищёнными от дублирования.

# 22. Главная цель проекта

Persephone Music должна стать персональной музыкальной экосистемой, а не просто сервером для раздачи файлов.

Система должна постепенно узнавать музыкальные предпочтения каждого пользователя, понимать его привычки, предлагать новую музыку, учитывать контекст прослушивания и заранее готовить нужные композиции.

Общая библиотека — инфраструктурная основа.

Пользовательские профили — основа персонализации.

Recommendation Engine — интеллектуальное ядро.

Prefetch Engine — механизм, который превращает рекомендации в готовую к прослушиванию музыку.

**Главный принцип: одна музыкальная библиотека, множество независимых музыкальных миров.**
